# Modern Web Guidance review — 2026-10-01

## What this is

A one-off review of the frontend (`frontend/src/**`) against current web-platform best
practices, run via the `modern-web-guidance` Claude Code plugin
(`GoogleChrome/modern-web-guidance`, installed this session from the `googlechrome` marketplace).
Scope: layout, forms/inputs, theming, dialogs/modals, drag-and-drop, and general frontend
patterns. Not a security review, not a functional/behavioral review, and not scoped to a
particular spec — a standalone quality pass requested directly in chat.

## What was done

1. Invoked the `modern-web-guidance:modern-web-guidance` skill (the plugin's search tool over a
   library of platform-feature guides, each with Baseline support data and fallback strategies).
2. Read through the frontend source tree (`components/`, `theme.css`, `index.css`, `utils/theme.ts`,
   `main.tsx`, `vite.config.ts`, `index.html`) to build a picture of current patterns: the `Modal`
   component, theme/dark-mode handling, form components (`ActivityForm`, `AssignActivityPicker`,
   `Settings`), the weekly planner grid, and the weekend bucket list's drag-and-drop reordering.
3. Ran a series of `npx modern-web-guidance search "<query>"` lookups (drag-and-drop reordering,
   accessible dialogs, form validation timing, segmented/tab controls, dark mode, loading states)
   and retrieved the full guides for the strongest matches:
   - `required-field-feedback` / `validate-input-after-interaction` / `accessible-error-announcement`
   - `light-dismiss-a-dialog` / `platform-controls-dismiss-dialog`
   - `dark-mode` / `component-specific-light-dark-theme`
   - `declarative-dialog-popover-control`
4. Cross-checked each guide's "MANDATORY"/fallback requirements against the actual implementation
   (not just whether a feature was used, but whether the required fallback/accessibility bridge was
   present too) before writing up a finding.

No code was changed as part of this review — it's a findings-only pass. The user was asked at the
end whether to act on any of them; none had been actioned as of this writing.

## Findings

### Already following current best practice

- **`Modal.tsx`** — real `<dialog>` + `showModal()`, proper focus restore on close, `::backdrop`
  styling. Its manual click-outside-to-close JS is exactly the fallback pattern the `light-dismiss-a-dialog`
  guide specifies for browsers without the `closedby` attribute (Safari still lacks it as of this
  guide's data).
- **Theming** (`theme.css` / `utils/theme.ts`) — `color-scheme` set on `:root`, `prefers-color-scheme`
  respected with a `data-theme` override path for explicit user choice, `accent-color` used instead
  of reimplementing checkboxes/radios from scratch. The FOUC fix (`applyStoredTheme()` called
  synchronously in `main.tsx` before `createRoot().render()`) matches the guide's recommended
  pattern.
- **`:has()`** already used for styled radio "pills" (`WeeklyPlanner.module.css:60`,
  `Settings.module.css:23`, `AssignActivityPicker.module.css:53`, `ActivityBank.module.css:25,85`)
  instead of extra JS/class-toggling state.
- **`prefers-reduced-motion`** gates the button hover transition in `index.css:85`.
- **Loading/busy states** use the semantic `<output>` element (e.g. `AssignActivityPicker.tsx:185,240`,
  `ActivityForm.tsx:142`) rather than a generic `<div aria-live>`.
- **Keyboard-only reordering** (Move up/down buttons in `BucketList.tsx`) exists as a first-class
  alternative to drag, not just a mouse-only affordance.

### Worth considering

1. **Form validation timing** (`ActivityForm.tsx` and similar) — errors are only computed in
   `handleSubmit`, via a hand-rolled `validationError` state, with no `required` attribute or
   `:user-invalid` usage. `:user-invalid`/`:user-valid` have been Baseline widely-available since
   2023-11, so no fallback burden — switching would give "don't show red until the user's actually
   left the field" and native focus-first-invalid-field-on-submit behavior for free.
2. **`<dialog closedby="any">`** — `Modal.tsx` already implements the JS fallback the guide specifies
   for non-supporting browsers, so adding `closedby="any"` to the dialog element is a no-cost
   progressive enhancement: native light-dismiss + back-gesture dismiss on mobile for the browsers
   that already support it (Chrome/Edge/Firefox since early-mid 2025; Safari still pending).
3. **Missing `<meta name="color-scheme" content="light dark">`** in `index.html` — the CSS property
   is already set, but the guide calls the `<meta>` tag out as the extra step that avoids any
   residual native-UI flash before CSS parses. One line, no downside.
4. **Settings' three-state theme toggle** (`Settings.tsx:17-21`, System/Light/Dark) — the `dark-mode`
   guide argues for a two-state toggle (System vs. "pinned opposite") since two of the three options
   always render identically. The existing "Currently: Dark/Light" hint text already mitigates the
   guide's main complaint (lack of feedback), so this reads as a legitimate judgment call rather
   than a bug — noted because it's an explicit recommendation in the guide, not because the current
   choice is wrong.
5. **Bucket list drag-and-drop** (`BucketList.tsx` + `OccurrenceItem.tsx`) uses the native HTML5
   Drag and Drop API (`draggable`, `onDragStart/Over/Drop`), which has no touch support at all
   without a polyfill — on a phone/tablet, only the Move up/down buttons work; drag does nothing.
   No guide in the plugin's library covers a drop-in replacement for this, so this is general
   platform knowledge rather than a specific guide finding: worth a conscious decision (desktop-only
   drag is fine if mobile reordering isn't a real use case; Pointer-Events-based reordering would be
   the fix if it is).

### Low-priority / optional

- `theme.css` repeats the same five custom-property block three times (`prefers-color-scheme`,
  `[data-theme='light']`, `[data-theme='dark']`). `light-dark()` (Baseline since 2024-05) could
  collapse this to one set of tokens — a maintainability win, not a correctness issue.
- `AssignActivityPicker.tsx:72-88` fires one `activityApi.getAll()` then an N+1 fan-out of
  `subTaskApi.getAll(activity.id)` per activity. Parallelized via `Promise.all`, so not a waterfall,
  but still N+1 round trips. This is an API/backend-shape concern, outside what this skill covers —
  worth knowing if the activity list grows.
