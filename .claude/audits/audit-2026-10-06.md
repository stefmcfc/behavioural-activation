# Non-Functional Audit — 2026-10-06

**Scope**: test coverage/variety, test execution efficiency, refactoring opportunities, performance
tuning. Requested by the user as a general health-check, not tied to a specific bug or feature.

**Method**: four independent research passes (one per area below), each read-only — no code
changed as part of this audit. Findings are backed by direct file reads, greps, and (for test
timing) a real `gradlew.bat test` / `npm test` run, not estimates.

**Disposition**: see [Recommendations](#recommendations) at the end for what became a spec, a spec
candidate, or a future idea.

**None automated.** No Playwright/Cypress/Selenium anywhere in the repo. Several specs explicitly

### Smoke tests

One exists on the backend: `BehaviouralActivationApplicationSpec` (context-load-only). No
equivalent frontend smoke test. No CI at all — confirmed in both `CLAUDE.md` and `tech.md`.

### Coverage gaps

- **No code-coverage tool is actually running.** Backend has no JaCoCo configured. Frontend has
  `@vitest/coverage-v8` *installed* as a devDependency, but there's no `test:coverage` script — the
  package sits unused.
- Spot-checked 10 recent ACs (6 backend, 4 frontend) against their named tests — all 10 traced
  cleanly to a real test. No drift found in this sample, but it's a sample, not a number.

### Test pyramid balance

41% of backend spec files (14 of 34) boot a real Spring context against real Postgres — heavier
than typical for this codebase's size. This is a deliberate, stated policy (`planner_spec_010`'s own
rationale: "real per-week counts and cross-row behaviour a mocked repository can't meaningfully
prove"), not drift. The cost is several concurrent Spring contexts/connection pools per test run —
covered in detail in the next section.

## 2. Test execution efficiency & isolation

The user asked specifically about parallel execution and per-class isolated database pools, citing
a pattern from a different project:

```groovy
@DynamicPropertySource
static void isolatedDatabase(DynamicPropertyRegistry registry) {
  registry.add("spring.datasource.url", { -> IsolatedTestDatabase.urlFor(SeriesControllerLookupSpec) })
}
```

**That pattern doesn't transfer here, and it's worth being explicit about why.** It exists to solve
SQLite's single-writer lock contention (`SQLITE_BUSY`) under concurrent connections. This project
uses real Postgres, with real MVCC and real concurrent-connection support — the problem that
pattern solves doesn't exist in this codebase.

### What's actually configured

- **Parallel execution**: off. `build.gradle.kts`'s `test { }` block only sets
  `useJUnitPlatform()` — no `maxParallelForks`, no JUnit Jupiter parallel-execution properties. The
  whole backend suite runs single-threaded, single-JVM.
- **Database provisioning**: one shared Postgres instance (`docker-compose.yml`), one shared test
  database. No per-class isolation anywhere.
- **Spring context count, measured**: a clean `gradlew.bat test --rerun-tasks` run created exactly
  **5 distinct Hikari connection pools** — not 16 (one per `@SpringBootTest` class would be the
  worst case). No `@MockitoBean`/`@ActiveProfiles` variation drives this; the only customization
  found anywhere is `@DynamicPropertySource`, used in 4 classes, 3 of which just enable Hibernate
  statistics for the query-count specs.
- **Connection pool sizing**: no `spring.datasource.hikari.maximum-pool-size` override exists
  anywhere (Hikari default is 10/pool). Worst case ≈ 50 connections across 5 pools, against
  Postgres's default `max_connections` of 100.

### Measured run times

| Suite | Tests | Wall-clock |
|---|---|---|
| Backend (`gradlew.bat test --rerun-tasks`) | 327, 34 classes | 27.6s |
| Frontend (`npm test -- --run`) | 652, 44 files | 15–17s |

Frontend is already running test files concurrently via Vitest's defaults — no config needed there.

### Verdict

- **Not a real problem today**: connection-pool exhaustion isn't close to happening (≤50 of 100
  available), and the SQLite-style isolated-database pattern simply doesn't apply to this Postgres
  setup.
- **One real, currently-unused lever**: JUnit Platform parallel execution. Backend tests at 27.6s
  aren't slow enough to need it yet, and turning it on isn't free — the 7 integration specs share
  one Postgres database, so each one's cleanup strategy would need checking first to avoid
  cross-test interference once they run concurrently. Worth doing once the suite is slow enough to
  actually annoy someone, not before.

## 4. Performance tuning

Checked specifically against the three already-fixed N+1 specs (`planner_spec_017`/`018`/`019`) to
confirm nothing has regressed. **Nothing has.** `SubTaskService.reorder()`/`delete()` (the newest
code) correctly reuses the bulk-fetch pattern those specs established; `ActivityPickerList.tsx`
still uses the bulk endpoints, not a per-activity fan-out.

| Finding | Detail | Worth fixing now? |
|---|---|---|
| `migrateStaleBucketItems` has no covering index | Runs on every `GET /api/v1/plan`; its sibling queries have full composite-index coverage, this one doesn't | No — sub-millisecond at realistic bucket-list sizes (low tens of rows) |
| `SubTaskList`/`BucketList` re-sort on every render, uncached | No `useMemo` around the `.sort()` call | No — largest real observed list is 12 items |

This is a single-user V1 app. Every finding in this section is real but below the threshold where
fixing it would be anything other than premature optimization, which this project's own conventions
explicitly argue against.

## Recommendations

Ranked by value-for-effort. Nothing here is urgent.

1. **`getErrorMessage()` dedup** — quick, zero-risk cleanup. → tooling spec.
2. **`ChevronIcon` collision** — quick; introduced sharper edge of this today while adding the
   `direction` prop. → tooling spec.
3. **Frontend coverage script** — one `package.json` line away from using an already-installed
   dependency. → tooling spec.
4. **CI + automated e2e** — the biggest structural gap, but also the biggest lift (tool choice,
   pipeline design, what runs on every push vs. nightly). Needs a real scoping conversation before
   it's spec-able. → spec candidate.
5. **JUnit parallel test execution** — real lever, not yet worth pulling at today's suite size. →
   future idea.
6. **`migrateStaleBucketItems` index / `useMemo` on list sorts** — real but sub-threshold at current
   data volumes. → future idea.

## Addendum — 2026-10-06, pagination scoping follow-up

A separate research pass, prompted by the user asking to scope the pre-existing "Pagination on `GET
/api/v1/activities`" future idea into a real spec. Logged here because it's the same kind of
list-fetching/performance territory this audit already covers, even though it came from a different
starting question.

**Pagination itself: reaffirmed not worth building**, with sharper reasoning than the original
entry. Real dev data (queried live): **20 activities, 23 sub-tasks total**. More importantly,
`ActivityBank.tsx`'s category grouping and "Favourites only" filter both operate client-side over
the *entire* fetched list — server-side pagination would actively conflict with that, not just be
unnecessary. See `future_ideas.md`'s updated entry for the full reasoning.

**One real, separate bug found along the way**: `TodayView.tsx` let its activity drawer and Assign
modal be open at the same time — nothing connected the two independent `useState`/hook values
tracking them. This directly violated a comment in `ActivityPickerList.tsx` claiming the two picker
modes are "never mounted simultaneously," and caused two independent `ActivityPickerList` instances
to each fetch the same bulk activity/sub-task data concurrently. Fixed via
`frontend_spec_048_today_view_picker_mutual_exclusion.md` — opening either picker now closes the
other. Real-browser verified both directions.

**Caching clarification** (asked directly by the user after the fix shipped): there is **no
caching anywhere in this fetch path, by design**. `ActivityPickerList`'s `Promise.all([activityApi.getAll(),
subTaskApi.getAllForOwner()])` runs fresh on every single mount — opening the drawer, closing it,
and reopening it seconds later refetches from scratch every time, with no memoization or TTL layer.
This was a deliberate choice, not an oversight the `frontend_spec_048` fix happened to leave
alone:

- **Correctness**: a live fetch always shows current data. Caching would need real invalidation
  tied to every activity/sub-task create/edit/delete/archive elsewhere in the app, or risk showing
  stale state.
- **Scale**: 20 activities / 23 sub-tasks is trivially fast to fetch fresh every time — there's no
  measurable cost to trade against that staleness risk at today's data volume.

This is the second of the two items this follow-up pass could have turned into work but didn't —
logged in `future_ideas.md` alongside the pagination entry, revisit only if real usage ever makes a
live fetch feel slow in practice.
